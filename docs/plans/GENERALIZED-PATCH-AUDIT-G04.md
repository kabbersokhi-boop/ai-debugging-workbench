## Product audit and reuse

The local application already admits immutable GitHub snapshots, production-only patches,
typed ordinary plans, separately justified requirements and validated independent plans.
Owner confirmation, isolated execution, downloads, history, response-selection guards and
bounded restart recovery exist. Reuse these contracts and evaluators unchanged.
Prepared Python examples and authentic recorded Boltons evidence already work. G3 and its
Node addendum have separately validated retained views. The recorded image contains only
the recorded server, frontend and recordings, with no local execution authority.

The first screen currently foregrounds prepared tasks; generalized intake is behind a
selector. Campaign tables precede intake. Requirement authoring begins with a large JSON
document, approval dumps the entire plan, and result identities are buried in raw evidence.
Desktop/mobile use the same working components, but need clearer hierarchy, form sizing,
focus treatment and contextual status explanations. README still describes G1-era limits.

## Intended journeys

- Beginner: understand the two check sets; choose **Audit a completed patch**; pin source,
  admit patch, review tests, optionally specify trustworthy requirements, validate controls,
  approve exact execution, inspect evidence and reopen history. Context explains Docker,
  local ownership, supported environments and why missing independent checks are not a pass.
- Experienced reviewer: open authentic saved evidence immediately; inspect immutable source,
  patch, ordinary plan, requirement provenance, controls and expected/observed data; download
  evidence. G3 campaign/addendum remain separate and accessible without dominating intake.

## Exact implementation

1. Cohesive accessible product header, six-step workflow navigation and context, retaining
   prepared examples, generalized intake and history. Reuse existing components.
2. Local-only public GitHub PR **metadata preview**: canonical github.com PR URLs, fixed
   unauthenticated api.github.com destination, bounded response/time, no redirects or code
   execution. Show observed base/head SHAs and counts; explicitly no admitted candidate or
   execution authorization. Manual immutable source admission recomputes tree identities.
   Full PR import is excluded: PR base tip need not be the diff's merge-base and changed
   test/configuration files cannot bypass existing admission restrictions.
3. Guided single-requirement authoring with explicit provenance/justification, function and
   finite assertions; retain advanced JSON for multi-requirement authors. Preserve exact
   approval, validation controls, versioning and invalidation on edits.
4. Result summary with separate ordinary/independent conclusions, visible immutable context,
   expected/observed evidence, scope caveats, downloads and saved history. No invented counts.
5. Recorded-only introduction and authentic Boltons case study with honest provenance and
   separate study accounting. No new public API authority or new recorded scientific data.
6. README, concise Mermaid trust-boundary diagram, practical first-audit instructions,
   actual desktop/mobile screenshots and G4 engineering report.

## Non-goals and invariants

No new evaluator/storage architecture, research campaign, language, model inference, agents,
autonomous oracle, GitHub writes, SaaS, video, merge, tag, release or deployment. G3 is closed.
Do not modify accepted campaigns, candidates, verifier definitions, recordings or hashes.
No unsafe HTTP destinations, tokens, mutable-ref admission or automatic installation/tests.
Approval must bind exact source/candidate/plans and be invalidated on edits. Missing checks,
unsupported inputs and infrastructure failures never imply correctness. Required DB and
recovery checks precede health. Public image remains physically separate, credential-free,
without generalized import/execution/recovery routes or Docker/host mounts.
